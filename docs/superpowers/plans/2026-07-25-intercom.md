# Plan 3 — Intercom: a real transport

**Branch:** `feat/subagent-kill` (continues after Plan 1)
**Schema:** this plan takes **v5**. Plan 2 (DB tiering) takes **v6**. Do not renumber v4.

---

## Why

Intercom today is fire-and-hope:

- `sendIntercom` (`packages/subagents/src/intercom.ts`) emits `SUBAGENT_RESULT_INTERCOM_EVENT`
  on `pi.events` and waits up to 10s for a `...DELIVERY_EVENT` reply carrying the same
  `requestId`. Delivery depends entirely on **an external broker being loaded and listening**.
  If nothing answers, it times out and reports `delivered: false`.
- On both the success and timeout paths it calls `mirrorMessage`, which does a single
  `INSERT INTO message_mirror`. **Nothing in the codebase ever reads that table.** It is a
  dead-letter box, not a queue.
- Child subagents have no escalation channel at all. A blocked child fails silently; the
  orchestrator learns nothing until the run ends.

Observed live: `spider message` to a running subagent returned `Session not found` — subagent
runs are not addressable as peer sessions, and there is no durable fallback.

## What we build

Two channels, per the approved design:

| Channel | Mechanism | Schema change |
|---|---|---|
| **A. Child → parent escalation** | rides existing `run_events` with `type='escalation'` | **none** — `run_events.type` is free text |
| **B. Session ↔ session** | promote `message_mirror` to a durable queue with delivery state + a poller | **v5** — `delivered_at`, `read_at`, index |

Channel B stops depending on the broker for *durability*. The broker (if present) stays as a
fast path for live delivery; the queue is the source of truth and the fallback.

## Test discipline (binding — Plan 1 shipped 8 defects of one class)

Plan 1 produced eight defects that all had the same shape: **the unit was correct and its
wiring was unverified**. Every one traced to test design in the plan, not implementer error.
These rules are mandatory for every task below.

1. **A regression test must never supply the value whose absence is the bug.**
   Plan 1's kill-wiring test constructed the `actions` object itself, when the bug was
   *"production never passes `actions`"*. It could not fail.
2. **Every test must name the specific mutation it would catch.** Put it in a comment.
3. **Any task that adds a user-facing surface needs at least one test that enters through the
   real entry point** — `dispatch()`, the hook, the mount seam — not the unit beneath it.
   `spider kill` shipped unreachable behind 13 green tests that all called the handler directly.
4. **Verify the mutation actually applied** before believing the result — insert a `/*MUT*/`
   marker and `grep -c` for it. A mutation that silently no-ops looks exactly like a passing
   test, and it fails in the direction that looks like good news.
5. **Test doubles adapt to the production contract, never the reverse.**

## Task 1 — Global migrations + schema v5

**Files:** `packages/db-core/src/migrate.ts`, `packages/db-core/src/schema.ts`,
`packages/db-core/src/__tests__/migrate.test.ts`

**The blocker this fixes:** `migrate.ts` currently applies steps only for project scope —
`const steps = scope === "project" ? PROJECT_MIGRATIONS[v] ?? [] : [];`. `message_mirror` lives
in the **global** schema, so without global migration machinery an existing global DB can never
gain the new columns.

1. Bump `SCHEMA_VERSION` 4 → **5**.
2. Add `GLOBAL_MIGRATIONS: Record<number, readonly string[]>` alongside `PROJECT_MIGRATIONS`,
   and select on scope: `scope === "project" ? PROJECT_MIGRATIONS[v] : GLOBAL_MIGRATIONS[v]`.
3. `GLOBAL_MIGRATIONS[5]`: `ALTER TABLE message_mirror ADD COLUMN delivered_at INTEGER`,
   `ALTER TABLE message_mirror ADD COLUMN read_at INTEGER`, plus
   `CREATE INDEX IF NOT EXISTS idx_mm_to_undelivered ON message_mirror(to_session, delivered_at)`.
4. `PROJECT_MIGRATIONS[5]`: none needed — but confirm a project DB at v4 still migrates to v5
   cleanly (version bump only).
5. Mirror the same columns into the fresh-install `message_mirror` DDL in `schema.ts`, so the
   fresh path and the migrated path end identical.

**Tests** (each names its mutation):
- a v4 global DB migrates to v5 and gains both columns, preserving existing rows
  (*mutation: drop the scope selection → global steps never run → columns missing*)
- a v4 project DB migrates to v5 without error
- fresh global DB has the columns (fresh path == migrated path — assert the actual column set
  of both and compare; do not assert a hardcoded list twice)
- migration is idempotent: opening twice is a no-op

**Verification:** the fresh-vs-migrated column comparison is the important one. Plan 1's schema
review confirmed fresh/migrated parity by hand; here it must be a test.

## Task 2 — `MessageStore`: a real queue

**Files:** new `packages/subagents/src/message-store.ts`,
new `packages/subagents/src/__tests__/message-store.test.ts`

Backed by the **global** DB (`message_mirror`).

```ts
export interface MessageRow {
  id: number; fromSession: string | null; toSession: string | null;
  kind: string | null; body: string | null;
  createdAt: number; deliveredAt: number | null; readAt: number | null;
}
export class MessageStore {
  constructor(globalDb: Db);
  enqueue(m: { fromSession?: string; toSession: string; kind?: string; body: string }): number;
  /** Undelivered messages addressed to `sessionId`, oldest first. */
  pending(sessionId: string, limit?: number): MessageRow[];
  markDelivered(id: number, now?: number): boolean;
  markRead(id: number, now?: number): boolean;
}
```

- `markDelivered`/`markRead` must be **guarded** — only transition when not already set — and
  return whether they changed a row. (Plan 1's C2 was caused precisely by an unguarded
  `finish()` overwriting a guarded `cancel()`. Guard symmetry is not optional.)
- `pending` must not return messages already delivered.

**Tests:** enqueue→pending round-trip; `pending` excludes delivered; `markDelivered` is
idempotent and returns `false` the second time; `markRead` likewise; ordering is oldest-first.
*Mutation for the guard: drop the `AND delivered_at IS NULL` → the idempotency test must fail.*

## Task 5 — Rewire the `message` action onto the queue

**Files:** `packages/subagents/src/intercom.ts`, `packages/subagents/src/actions/message.ts`,
`packages/host/src/hooks.ts` (poller wiring), tests for each.

1. `sendIntercom` keeps the broker fast path but **always enqueues first** via `MessageStore`.
   Delivery state comes from the queue, not solely from the broker reply:
   - enqueue → attempt broker delivery → on ack, `markDelivered`.
   - on timeout/no broker, the row simply stays pending. This is **not an error** — it is
     queued for the recipient's poller. The result must say so.
2. The `message` action's result must distinguish **queued** from **delivered** from **failed**,
   and must not report a plain failure for a message that is durably queued. Today it returns
   `isError: !delivered`, which mislabels a queued message as an error.
3. Add a **poller**: on `session_start` (wire from `packages/host/src/hooks.ts`, which already
   resolves and opens DBs), drain `pending(sessionId)` and deliver to the session, marking
   each delivered. Keep it best-effort and non-blocking — a poller failure must never break
   session start. Follow the reaper's precedent for surfacing failure rather than swallowing it
   (that was an Important finding in Plan 1 Task 7).

**Tests:**
- enqueue happens even when the broker never acks (*mutation: remove the enqueue → fails*)
- a queued-but-undelivered message is NOT reported as an error
- an acked message is marked delivered
- the poller drains pending messages for the starting session and marks them delivered
- the poller leaves messages addressed to OTHER sessions alone

**Boundary requirement (rule 3):** one test must go through the real `dispatch({action:"message"})`
path, not `makeMessageHandler()` directly. `spider kill` shipped unreachable because no test
crossed `dispatch()`.

## Task 6 — Teach subagents to escalate

**Files:** `packages/superpowers/src/agentsmd-content.ts`, and wherever the child system prompt
is assembled (`packages/subagents/src/pi-args.ts` — `systemPrompt` / `--append-system-prompt`).

The diagnosis from the user: *subagents don't know to use intercom, and escalation to the
supervisor must be part of subagent instructions.*

- Add an explicit, unhedged instruction to the child's appended system prompt: when blocked,
  uncertain about scope, or about to do something destructive/irreversible, **escalate to the
  orchestrator** rather than guessing or failing silently — and state exactly how.
- No soft verbs. Plan 1 proved "prefer X when Y" decays to nothing. Say "you MUST".
- Mirror the rule in the managed AGENTS.md block for the top-level agent.

**Tests:** the composed child prompt contains the escalation instruction
(*mutation: delete the instruction → fails*). Keep the assertion on a stable substring, not the
entire paragraph, so wording tweaks do not cause false failures.
